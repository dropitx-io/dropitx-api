# Phase 1 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Scope Finding — No Visual UI Surface Exists

This phase (`dropitx-api`) is a FastAPI backend. Its six requirements
(SEC-01..06) are auth-guard fixes, rate-limit additions, and a one-character
bug fix (`true` → `True`) across existing JSON API routes — see
`01-RESEARCH.md`. There is no HTML page, template, rendered component, or any
other visual surface anywhere in this phase's scope. `components.json`,
`tailwind.config.*`, and `postcss.config.*` do not exist in this repo
(confirmed by directory scan). The "frontend" mention that triggered the
ui-plan-gate heuristic is `PROJECT.md`'s out-of-scope note about the sibling
`dropitx/` Next.js repo — not this repo.

Per explicit user instruction, this UI-SPEC does not invent a design system,
color palette, or typography scale for a phase that has none. Every section
below that assumes a rendered UI (Design System, Spacing Scale, Typography,
Color, Registry Safety) is marked **Not Applicable** with the reason stated.

What *does* exist, and *is* a legitimate interaction contract worth locking
for this phase: the shape of the JSON responses (status codes, error
envelope, headers) that SEC-01 through SEC-06 introduce or change. API
consumers (the `dropitx` frontend, the `dropitx-cli`, third-party API-key
users) depend on these being consistent. That contract is specified in
**API Response Contract** below, and doubles for this template's
`Copywriting Contract` and `UI Considerations` sections (state coverage —
just HTTP response states instead of rendered UI states).

## API Response Contract

This is the actual interaction contract for this phase. Every new or changed
response introduced by SEC-01..06 must match one of the shapes below exactly
— reusing the codebase's existing conventions (verified by reading
`app/public/shares.py`, `app/public/oembed.py`, `app/internal/upload.py`,
`app/public/encryption.py` this session), not inventing new ones.

### Envelope

All error responses are FastAPI's default `HTTPException` JSON body — `core/exceptions.py`'s
`ErrorResponse` model (`{error, detail, request_id}`) is defined but **never
wired to any exception handler anywhere in this codebase** (verified: no
`@app.exception_handler` registrations exist, `ErrorResponse` has zero other
references). Do not adopt `ErrorResponse`'s shape for this phase's fixes —
that would make these six routes inconsistent with every other route in the
API today. Match what actually ships:

```json
{"detail": "<human-readable message>"}
```

Success responses (SEC-06) are the route's existing normal JSON body,
unchanged shape — just no longer a 500.

### Per-requirement contract

| Req | Route | New/changed response | Status | Body | Headers |
|-----|-------|----------------------|--------|------|---------|
| SEC-01 | `POST /shares/{slug}/encrypt` | No user, no `delete_token` | 401 | `{"detail": "Authentication required"}` | none |
| SEC-01 | `POST /shares/{slug}/encrypt` | User is not owner, token doesn't match | 403 | `{"detail": "Not authorized to modify this share"}` | none |
| SEC-02 | `POST /shares/{slug}/reencrypt` | Rate exceeded | 429 | `{"detail": "Too many attempts. Try again later."}` | `Retry-After: <seconds>` |
| SEC-03 | `GET /api/download/group/{slug}` | Rate exceeded | 429 | `{"detail": "Rate limit exceeded"}` | `Retry-After: <seconds>` |
| SEC-04 | `GET /shares/{slug}/content`, `/download`, `/preview` | Rate exceeded | 429 | `{"detail": "Rate limit exceeded"}` | `Retry-After: <seconds>` |
| SEC-05 | `GET /api/dashboard/domains/resolve/{domain}` | Rate exceeded | 429 | `{"detail": "Rate limit exceeded"}` | `Retry-After: <seconds>` |
| SEC-06 | `GET /api/u/{username}` | Public profile exists | 200 | unchanged existing profile JSON shape | none |
| SEC-06 | `GET /api/u/{username}` | Profile not found/not public | 404 | `{"detail": "Profile not found"}` (existing, unaffected by this fix) | none |

**Locked decisions this table makes (so planner/executor don't re-derive them):**

1. **401 vs 403 wording for SEC-01 reuses existing verbatim strings** —
   `"Authentication required"` (matches `set_password`/`burn_share`/`delete_share`
   at `app/public/shares.py:306,328,445`) and `"Not authorized to modify this
   share"` (matches `_authorize_owner`'s existing raise at
   `app/public/encryption.py:105` / `app/public/shares.py:135`, verbatim, no
   new string). Do not paraphrase these.
2. **SEC-02's 429 reuses `check_password_rate_limit`'s existing message
   verbatim** — `"Too many attempts. Try again later."` (from `unlock_share`,
   `app/public/shares.py:365`). No new string, since SEC-02 calls the same
   existing function, not a new one.
3. **SEC-03/04/05's 429 wording is standardized to `"Rate limit exceeded"`**
   — this is `check_upload_rate_limit`'s and `check_oembed_rate_limit`'s
   existing wording (`app/internal/upload.py:202`, `app/public/oembed.py:60`),
   not the two *different* strings RESEARCH.md's own code samples proposed
   (`"Too many requests. Try again later."` for bulk-download/public-read,
   `"Too many requests."` for domain-resolve). Introducing either of those
   would create a **third** distinct 429 message for the same class of
   fail-open cost/abuse limiting, alongside the two that already exist
   inconsistently in this codebase (see Known Pre-Existing Inconsistency
   below). Standardize on the existing, most common string instead of adding
   a new variant.
4. **`Retry-After` header is always present on 429s from this phase's new
   buckets**, even though the pre-existing `check_upload_rate_limit` call
   sites (`app/internal/upload.py`, `cli_upload.py`, `publish.py`, etc.) omit
   it today. New code should follow `check_oembed_rate_limit`'s more complete
   convention (`app/public/oembed.py:57-63`), not upload.py's. Do not "fix"
   the pre-existing upload.py omission as part of this phase — out of scope,
   flagged only as context.
5. **No route in this phase should introduce `core/exceptions.py`'s
   `ErrorResponse` model or a new exception handler.** That would be a
   larger, cross-cutting refactor (touching every route's response shape),
   explicitly out of scope per `01-RESEARCH.md`'s Anti-Patterns section
   ("no refactors, no new modules"). If the project ever wants a uniform
   error envelope, that belongs in a dedicated phase, not smuggled into a
   6-item security patch.

### Known pre-existing inconsistency (informational, not this phase's fix)

`app/internal/upload.py`'s `check_upload_rate_limit` call sites raise 429
with `detail="Rate limit exceeded"` but **no `Retry-After` header**, while
`app/public/oembed.py`'s call to the same rate-limit family includes the
header. This phase's new buckets (SEC-03/04/05) should follow oembed's
complete pattern (message + header), not upload's. Fixing upload.py's
missing header is out of scope here — note it only so the executor doesn't
copy the incomplete version by picking the wrong sibling to mirror.
