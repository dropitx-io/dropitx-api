<objective>
Fix the confirmed-live, blocking bug in `provision_firebase_user` (ambiguous `user_id` column reference between the `RETURNS TABLE` OUT parameter and the `user_profiles.user_id` column) so that `GET /api/auth/session` — the sole provisioning entrypoint for Firebase-authenticated users — actually works against a real Postgres instance, then prove it with a live-DB integration test covering the single-caller flow and the concurrent-first-login race.

This is the phase's tracer: AUTH-02 and AUTH-03 cannot pass in practice until this RPC works, regardless of any other task in this phase. 02-RESEARCH.md already reproduced this bug live and designed/verified the fix; this plan applies that verified fix to the actual source files and to the running database, then locks it in with a new automated test (the gap the original design spec asked for and that the existing mocked `tests/test_auth_session.py` structurally cannot catch, since it mocks `get_admin_client()` entirely).

**Migration approach (resolves 02-RESEARCH.md Open Question 1):** ship the fix as a new file, `migrations/009_fix_provision_firebase_user.sql`, per 02-VALIDATION.md's Wave 0 Requirements — not an in-place edit of `migrations/008_provision_firebase_user.sql`. `008` stays as an immutable historical record; `009` supersedes it via `CREATE OR REPLACE FUNCTION` (idempotent, safe to apply after `008` on any pre-existing DB). `infra/init/02_rpc_functions.sql` (the fresh-boot source of truth) is fixed in place since it has no migration history to preserve.

Purpose: Make DropItX's Firebase-based provisioning actually work, not just look correct in code review.
Output: A corrected RPC (in both `infra/init/` and a new migration), applied to the live local Postgres, verified by a new automated integration test covering both the single-caller and concurrent-caller cases.
</objective>
