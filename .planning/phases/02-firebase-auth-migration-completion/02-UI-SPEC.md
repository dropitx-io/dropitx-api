# Phase 2 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Scope Finding — No Visual UI Surface, and No New Consumer-Facing Response Contract Either

This phase (`dropitx-api`) is a FastAPI backend. Its five requirements
(AUTH-01..05) are: (1) verifying already-implemented Firebase JWT
verification and route wiring, (2) fixing an internal PL/pgSQL bug in the
`provision_firebase_user` RPC (`infra/init/02_rpc_functions.sql` /
`migrations/008_provision_firebase_user.sql`), (3) adding one live-DB
integration test, (4) adding an env var line to two `.env.example` files,
and (5) a documentation-accuracy pass removing stale Supabase-JWT
references — see `02-RESEARCH.md`. There is no HTML page, template,
rendered component, or any other visual surface anywhere in this phase's
scope. `components.json`, `tailwind.config.*`, and `postcss.config.*` do not
exist in this repo. The "frontend" mention that triggered the ui-plan-gate
heuristic is `PROJECT.md`'s out-of-scope note about the sibling `dropitx/`
Next.js repo — not this repo. This is the same pattern already confirmed by
the user for Phase 1 (`01-UI-SPEC.md`), applied consistently here.

**This phase is narrower than Phase 1 on the one axis where Phase 1 still
had a legitimate contract to lock.** Phase 1 introduced *new* HTTP response
shapes (401/403/429 bodies + headers on previously-unprotected routes), so
its UI-SPEC repurposed the Design System template sections into an API
Response Contract. Phase 2 does not: per `02-RESEARCH.md` and the phase's
own success criteria, `GET /api/auth/session`'s response shape
(`{ id, email, profile }` / `401 {"code": "user_not_provisioned"}`) is
**already fully specified** by the original design spec
(`docs/2026-08-12-firebase-auth-backend-api-design.md`) and is **unchanged**
by this phase — AUTH-01/02/03 fix the RPC bug *behind* that contract, they
do not alter its externally-visible shape, status codes, or field names. No
new route, no new response shape, no new error code is introduced anywhere
in this phase's scope.

**AUTH-04 and AUTH-05 do have narrow textual surfaces (env var line,
corrected doc sentences), but they don't need a separate contract here.**
`02-RESEARCH.md` already pins the exact content for both, more precisely
than a UI-SPEC would add: the env var line and placement (`.env.example` /
`.env.local.example`, matching the existing `SUPABASE_URL` block, per AUTH-04's
research entry and Wave 0 Gaps), and the full per-file, per-line Doc
Staleness Audit table (14 files, exact stale sentence + line number each) for
AUTH-05. Restating either here would duplicate that table rather than lock
anything new — it would not survive the "adds no value" bar this agent is
held to. The planner/executor should treat `02-RESEARCH.md`'s Doc Staleness
Audit table and Wave 0 Gaps section as the authoritative source for that
copy, not this file.

Given that, every section below that assumes a rendered UI, a component
system, or a new response/error contract is marked **Not Applicable**, with
the reason stated, rather than manufacturing a design contract this phase
has no use for.
